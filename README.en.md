[中文](README.md) | English

> A profile-level DeepSeek Harness plugin that stops models from silently
> hanging your agent when they emit tool calls as XML text instead of the
> structured `tool_calls` field — and fails loudly instead of silently when a
> response carries no executable content.

## The problem (observed in production, two independent cases)

**Case A — StepFun `step-5-preview`** (provider `step-plan-152`,
`https://api.stepfun.com/step_plan/v1`): the model *intermittently* returns
tool calls as Qwen/Hermes-style XML text inside `reasoning_content` instead
of the structured `tool_calls` deltas.

**Case B — gateway-routed `deepseek-v4.1-flash-max`** (via a local aggregating
gateway): after the primary account hit HTTP 429, the router fell back to an
upstream that returned tool calls as **Anthropic-style XML text**
(`parameter name="key"` with a name attribute), frequently **truncated**
mid-markup.

Both cases hit the same harness failure chain:

1. The model writes the tool call as XML **text** rather than structured
   `tool_calls`;
2. pi-ai's `openai-completions` parser only maps `delta.tool_calls` into
   `toolCall` blocks — the XML text just accumulates into the text/thinking
   block;
3. `dsh-agent-loop` (`lib/index.js:1152-1153`) treats "no tool-call blocks" as
   "turn completed":

   ```js
   const toolCalls = message.content.filter((block) => block.type === "tool-call");
   if (toolCalls.length === 0) return { kind: "completed" };
   ```

   The turn ends **silently** — no error, no retry, no tool execution. The
   user sees "it thought for a while, then nothing happened" / "the task got
   truncated".

## The fix (two layers, via the official `llm/stream` waterfall — no
`app.asar` modification, survives app updates)

1. **Text tool-call recovery.** After the stream ends, scan text/reasoning
   blocks for tool-call markup and promote matches to real `toolCall` blocks,
   rewriting the finish reason to `tool-calls` so the agent loop actually
   executes them. Supported formats:
   - Qwen/Hermes style: `tool_call` + `function=<name>` + one `parameter=<key>`
     element per argument;
   - Anthropic style: `function name="<name>"` (or `invoke name="<name>"`) +
     `parameter name="<key>"` per argument;
   - JSON form: `{"name": ..., "arguments": {...}}`.

   Guards (a normal model is never affected):
   - Only active when the response contains **no structured `tool_calls`**;
   - The tool name must be declared in the request's `tools` (so prose that
     merely mentions such markup is never executed; tool-less requests like
     compaction/session-title pass straight through);
   - Argument values are coerced to the types the tool's JSON Schema declares
     (number/integer/boolean/object/array), XML entities are decoded, and
     multi-line code keeps its indentation.

2. **Safety net.** When a response ends `stop` with nothing executable —
   thinking-only, empty text, or text that is *only* tool-call markup
   (complete-but-unparseable, truncated, or bare `parameter` elements) — the
   finish is rewritten to the retryable `EMPTY_RESPONSE` failure so the
   default retry policy (normal: 5 attempts, 500ms-10s backoff) retries
   instead of silently ending the turn. After retries are exhausted the user
   sees an explicit error.

## Install

Prerequisites: (1) DSH has been started at least once (`~/.dsh/profiles/desktop/` exists);
(2) Node **16.9+** (the plugin uses `Object.hasOwn`; check with `node --version`).

```powershell
# from the directory containing this README
.\install-stepfix.ps1
# or point at a specific profile / DSH home (use real quoted paths):
.\install-stepfix.ps1 -ProfileDir "C:\\path\\to\\profile" -DshHome "C:\\path\\to\\.dsh"
```

The script copies the package into `<profile>/node_modules/` and registers an
entry in `cordis.patch.yml`. Then **restart DeepSeek Harness** (the host reads
the patch file only at startup).

### ⚠️ Patch-entry gotcha (cost me a restart cycle)

`cordis.patch.yml` entries are **patches**: a plain `- id:` entry can only
*modify* an existing entry. A brand-new id is silently skipped by
`applyEntryPatches` (warning only, invisible in GUI mode). To **add** a plugin
you must use the `insert` form:

```yaml
- insert:
    - id: text-tool-call-recovery
      name: "@zhaozehao10/dsh-text-tool-call-recovery"
```

Verify with `dsh --profile <copy-of-profile> --dump-config` (the CLI refuses
the Electron-managed `desktop` profile, so test on a copy). Note the GUI
plugin manager lists *registry-installed packages* — patch-inserted entries do
not appear there, so "not in the manager" is not evidence of "not loaded".

### Manual install (if you would rather not run the script)

1. Copy `lib/` and `package.json` into
   `<profile>/node_modules/@zhaozehao10/dsh-text-tool-call-recovery/`
2. Append the `insert:` block shown above to `<profile>/cordis.patch.yml`
3. **Back it up first** (the script does this for you; manually, do it yourself):
   ```powershell
   Copy-Item "<profile>\cordis.patch.yml" "<profile>\cordis.patch.yml.bak"
   ```
4. **Self-check** that the plugin file is present and parses:
   ```powershell
   node --check "<profile>\node_modules\@zhaozehao10\dsh-text-tool-call-recovery\lib\index.js"
   ```
   No output means success (`node --check` only prints on a syntax error).
5. **You must restart DeepSeek Harness** — fully quit it (tray icon → Quit),
   not just close the window. The plugin's `apply()` runs only once, at process
   start; without a restart the running process keeps using the old code and
   you will conclude "I installed it and nothing happened". This applies
   **equally to the script and to a manual install**.
6. Confirm it took effect after the restart:
   ```powershell
   node test/hardening/live-instance.mjs
   ```

## Uninstall

1. **Preferred: restore from the backup** the installer made (it prints the path,
   e.g. `%TEMP%\dsh-install-backup\cordis.patch.yml.bak-YYYYMMDD-HHMMSS`).
   Copy it back over `cordis.patch.yml` — this is lossless.
2. Otherwise, edit `cordis.patch.yml` **by hand in a normal text editor**
   (Notepad / VS Code — *not* a PowerShell one-liner) and delete the two lines
   under `- insert:`:
   ```yaml
   - insert:
       - id: text-tool-call-recovery
         name: "@zhaozehao10/dsh-text-tool-call-recovery"
   ```
   > ⚠️ **Do not** rewrite the file with a `Get-Content` / `Set-Content` / `Out-File`
   > round-trip. The reason is **not** collapsed line breaks (that common claim does
   > not hold — measured: the line count stays the same); the real problem is that
   > `cordis.patch.yml` is **UTF-8 without BOM**, and PowerShell 5.1's
   > `Get-Content -Raw` (without `-Encoding`) decodes it as **ANSI/GBK**, so
   > **non-ASCII text is already corrupted on the way in** and no write-back can
   > repair it (`Set-Content -Encoding UTF8` also adds a BOM).
   >
   > If you must script it, read and write explicitly as UTF-8 using
   > `[System.IO.File]` with `UTF8Encoding($false)` to keep it BOM-free;
   > see the Chinese README's section 6 for the full snippet.
3. **Delete the plugin directory** — this is the second half of the uninstall and
   must not be skipped:
   ```powershell
   Remove-Item "<profile>\node_modules\@zhaozehao10\dsh-text-tool-call-recovery" -Recurse -Force
   ```

   > ⚠️ **Both halves are required.** If you delete only the directory and leave the
   > patch entry, the Cordis Loader will still try to load that entry on the next
   > start while the directory is gone — depending on the Loader version it either
   > errors or is silently skipped, and **neither is a clean uninstall**.
4. Restart the app.

Temporarily disable without uninstalling: the plugin checks the environment
variable `DSH_TEXT_TOOL_CALL_RECOVERY` inside `apply()` and, when it equals the
**string** `"0"`, registers no listener at all (equivalent to not installed).

> ⚠️ **Two gotchas, both matter**:
>
> **1. The variable must exist before DSH starts.** Environment variables are
> copied into a process **at start-up**; running `$env:... = "0"` in a separate
> PowerShell window does **not** propagate to an already-running DSH. Set a
> **user-level** variable, then **fully restart** DSH:
>
> ```powershell
> [Environment]::SetEnvironmentVariable("DSH_TEXT_TOOL_CALL_RECOVERY", "0", "User")
> # remove it when you are done, otherwise it stays disabled
> [Environment]::SetEnvironmentVariable("DSH_TEXT_TOOL_CALL_RECOVERY", $null, "User")
> ```
>
> **2. Only the exact string `"0"` counts.** `"false"`, `"off"`, `"no"`, `""`,
> `"00"` and `"0 "` (with a space) **do not disable** it — the plugin tests
> `=== "0"`. A wrong value reports no error, so you will believe it is disabled
> while it is still active.

## Known limits (honest list)

- **Recovery only runs when `finish.reason.kind === "stop"`**. Everything else is
  passed through untouched: `tool-calls` (the model already emitted structured
  calls), `error`, `aborted`, `max-tokens`.

  This is a deliberately conservative choice: a non-`stop` reason means upstream
  has already signalled that this is not a normal ending, and rewriting it could
  mask a real problem. The side effect is that if some gateway wrongly normalises
  `finish_reason` to `tool-calls` while the stream contains **no** native
  `tool-call` block, the recovery is **missed**. That combination has not been
  observed in real logs (under the normal openai-completions protocol you only
  get `finish_reason=tool_calls` when `tool_calls` are present).
  `hardening/mixed-native-recovery.mjs` documents the current behaviour.

- **When a native structured call is already present, nothing is recovered from
  text.** If a model emits `tool_calls` *and* repeats the call as XML text in the
  body, the plugin keeps only the native call.

  This prevents **double execution** (running the same `rm` / `git push` twice is
  unacceptable); the cost is that the extra text-form call is ignored. That
  duplication has also never been observed in real logs.

- **Qwen-style bare `<function=name>` is parsed only inside `<tool_call>`**:
  a bare `<function=pwsh>...</function>` with no outer `<tool_call>` is **not** recovered,
  because the bare-element pass only matches the quoted-attribute form `<function name="x">`.

  This is a **format boundary, not a bug**: the two spellings differ syntactically
  (`=` versus ` name="..."`), and one shared regex would also admit malformed forms
  such as `<function=a b>`. Measured: that shape falls through to the safety net
  (`EMPTY_RESPONSE`, then a retry) and is **never silently dropped**. Round 128
  confirmed every Qwen-style call in the real logs **carries the `<tool_call>` wrapper**,
  so this limit has not been hit in practice.

- **Only three markup families are parsed** (`<tool_call>` wrappers, bare
  `<function name=…>` / `<invoke name=…>` elements, and the `antml:`-prefixed
  Anthropic variants). Other dialects (e.g. `<tool><name>…</name></args></tool>`)
  are not parsed. Two distinct outcomes must be distinguished (measured in round 129):

  - if the text contains **any known marker** (e.g. `<tool_call>`) and the substantive
    text is under 20 characters with tags making up more than half of it, it is judged
    "markup only" and falls through to the safety net (`EMPTY_RESPONSE`, then a retry);
  - if the text contains **no known marker at all** (e.g. a pure
    `<tool><name>…</name></args></tool>`), it counts as visible text and `stop` is
    **passed through unchanged** — the turn ends normally, the reader sees the text,
    but it is not executed.

  Neither outcome executes the example and neither hangs; they differ only in
  "retry once" versus "end immediately".

- **Responses where the upstream loses output tokens while reporting `stop`**
  (observed from one gateway upstream: usage recorded 1,145 tokens but only
  ~40 tokens of content survived, no markup at all) cannot be detected from
  the chunk stream alone — the harness cannot distinguish that from a
  legitimately short reply. That one needs a routing-side fix.
- Tied to DSH 0.2.0-rc.2's `llm/stream` seam and StreamChunk protocol
  (verified to load and pass on 0.2.1-rc.1, 0.2.1-rc.2 and **0.2.1-rc.3** as well).
